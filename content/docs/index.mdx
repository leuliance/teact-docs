Teact lets you build Telegram bots the way you build React apps: **components**, **hooks**, **routing** and **JSX**, run with [Bun](https://bun.sh). You describe what a chat should show, and Teact works out which Telegram messages to send or edit, on top of [grammY](https://grammy.dev).

```tsx title="src/index.tsx"
import { createBot, useState } from "@teactjs/core";
import { Message, InlineKeyboard, Button } from "@teactjs/ui";
import { TelegramAdapter } from "@teactjs/telegram";

function Counter() {
  const [count, setCount] = useState(0);
  return (
    <Message text={`Count: ${count}`}>
      <InlineKeyboard columns={2}>
        <Button text="−1" onClick={() => setCount((c) => c - 1)} />
        <Button text="+1" onClick={() => setCount((c) => c + 1)} />
      </InlineKeyboard>
    </Message>
  );
}

export const bot = createBot({
  component: Counter,
  adapter: new TelegramAdapter(),
  commands: { start: { description: "Start the counter" } },
});

if (import.meta.main) bot.start();
```

Tapping a button does not post a new message. The click runs `setCount`, the component re-renders, and Teact edits the existing message to match.

## How Teact works

Teact is a custom React renderer. The pieces fit together like this:

1. **Updates come in.** The adapter (`TelegramAdapter` from `@teactjs/telegram`) receives Telegram updates by polling, a webhook server, or `bot.fetch(request)` on serverless, and hands each one to the engine as a platform-neutral `BotContext` (`chatId`, `userId`, `text`, `callbackData`, `raw`, …).
2. **Middleware runs.** Plugin middleware runs first, then your own `middleware`. A middleware can stop the update with `halt(ctx)`; otherwise the chain continues automatically.
3. **React renders.** The engine renders your `component` (or the route your `router` resolves) with `react-reconciler`. Components such as `<Message>`, `<InlineKeyboard>` and `<Button>` become host elements (`tg-message`, `tg-keyboard`, `tg-button`, …), and the reconciler produces an **output tree** of plain `{ type, props, children }` nodes.
4. **The adapter sends or edits.** On every commit the engine passes the output tree to the adapter. By default (`replace` mode) it **edits** the chat's last bot message when that is possible and **sends** a new one otherwise. The adapter serializes the tree into a Bot API call: `sendMessage`, `sendPhoto`, `editMessageText`, and so on.

### One root per chat

Every chat gets its own React root, keyed by platform and chat id. State from `useState` lives in that root, so two users never share it. Updates for the same chat are processed one at a time, in order; different chats run concurrently.

- A **button press** edits the message the button lives on.
- A **new text message** from the user makes the next render send a fresh message below it.
- A **registered command** (such as `/start`) or a **route button** resets the chat's root, so the screen starts from its initial state.

### Buttons and handlers

`<Button onClick={fn}>` registers `fn` in the chat's in-memory handler map and sends an opaque `callback_data` id. `<Button route="/settings">` encodes the route itself in the `callback_data`, so it works even after a restart. Prefer route buttons, or keep screen state in `useSession`, when you deploy to serverless (see [Deployment](/docs/guides/deployment)).

### Sessions

`useSession()` returns `[session, updateSession]` for the current chat. Sessions are read from a `SessionStore` before each render and written back after it. The default store is in memory; pass a durable one with `createBot({ session: { store } })`. See [Storage](/docs/guides/storage).

### Coming from grammY or Telegraf

Teact runs on grammY, so the Bot API concepts are the same. What changes is that you describe the screen instead of issuing replies.

| In grammY / Telegraf | In Teact |
| --- | --- |
| Handlers: `bot.command("start", …)`, `bot.on("message", …)` | Components. Register commands with `createBot({ commands: { start: { description, route: "/" } } })`; react to specific updates inside a component with `useOn("photo", handler)`, `useText()` or `useCallbackData()` |
| `ctx.reply(text, { reply_markup })` | Return `<Message text="…">` from a component. Re-renders edit the message; for quick text replies a command can use `handler: ({ reply }) => reply("…")` |
| `InlineKeyboard` builder / `Markup.inlineKeyboard` | `<InlineKeyboard>` with `<Button onClick>`, `<Button route>` or `<Button url>`; `<ReplyKeyboard>` for reply keyboards |
| `bot.callbackQuery("data", …)` | `onClick` on the `<Button>` itself; no callback data to match by hand |
| `session()` middleware and `ctx.session` | `useSession()` in any component; choose the store with `createBot({ session: { store } })` |
| Scenes / wizards, `@grammyjs/conversations` | `useConversation`, `useForm`, `<Conversation>` and `<Form>` from `@teactjs/core`; `conversationsPlugin()` from `@teactjs/telegram` for imperative grammY-style flows |
| `bot.use(middleware)` | `createBot({ middleware: [...] })`, with `halt(ctx)` to stop an update |
| `ctx.api` | `useTelegram()` returns `{ api, ctx, chat, from, chatId }` for raw access |

## What you can build

- **Messages and keyboards**: inline and reply keyboards with `<Button>`, `<InlineKeyboard>` and `<ReplyKeyboard>`.
- **Routing**: `createRouter` with params, `beforeLoad` guards, and navigation modes (`push`, `replace`, `stack`, `dismiss`).
- **Flows**: multi-step **conversations** and schema-driven **forms**.
- **Platform features**: **streaming** text, **i18n** with automatic language detection, **payments** (`useInvoice`), **auth** plugins, **session** storage, and **events** with `useOn`.
- **Databases**: durable storage and sessions on Redis, Postgres, SQLite, MongoDB, or Cloudflare D1/KV, on long-running servers and the edge.
- **Production plugins**: rate limiting, logging, maintenance mode, error reporting, analytics, feature flags and broadcasts.
- **Deploy anywhere**: long-running polling, a webhook server, or serverless through a web-standard `bot.fetch(request)` handler.

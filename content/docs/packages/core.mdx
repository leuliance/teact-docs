`@teactjs/core` is the engine. It contains the React reconciler that turns your components into
Telegram output, the runtime that drives a bot (`createBot`), the router, the plugin/DI host, and
**every hook**. It also re-exports the React primitives you need so you rarely import `react`
directly.

This is the single import for everything that isn't a visual component — components live in
[`@teactjs/ui`](/docs/packages/ui).

```bash
bun add @teactjs/core
```

```tsx
import { createBot, createRouter, useSession } from "@teactjs/core";
```

## Example

```tsx
import { createBot, createRouter, useSession } from "@teactjs/core";
import { Message, InlineKeyboard, Button } from "@teactjs/ui";
import { TelegramAdapter } from "@teactjs/telegram";

function Home() {
  const [session] = useSession<{ name?: string }>();
  return (
    <Message text={`Hi ${session.name ?? "there"}!`}>
      <InlineKeyboard>
        <Button text="About" route="/about" />
      </InlineKeyboard>
    </Message>
  );
}

const router = createRouter({
  "/": { component: Home, command: { name: "start", description: "Start" } },
});

const bot = createBot({ router, adapter: new TelegramAdapter() });

if (import.meta.main) bot.start();
```

See the [Router guide](/docs/guides/router) and [Hooks reference](/docs/guides/hooks) for details.

## The bot instance

`createBot(options)` returns a bot with these methods:

| Method | What it does |
| ------ | ------------ |
| `bot.start()` | Starts long polling (or the webhook server), registers the command menu, and handles SIGINT/SIGTERM. |
| `bot.stop()` | Unmounts every chat and runs the plugins' `onStop` hooks. |
| `bot.fetch(request, { token?, secretToken?, env? })` | Serverless/edge webhook handler: `Request → Response`. Initializes the bot lazily, once per isolate. |
| `bot.setCommands()` | Registers the command menu (Telegram `setMyCommands`) and resolves the number of commands. |

### `bot.fetch()` options

| Option | Description |
| ------ | ----------- |
| `token` | Bot token for this request (e.g. `env.TELEGRAM_BOT_TOKEN`). Falls back to `createBot({ token })` or `TELEGRAM_BOT_TOKEN`. |
| `secretToken` | Webhook secret. A request whose `X-Telegram-Bot-Api-Secret-Token` header doesn't match gets a `401` **before any initialization** (no `getMe`, no plugin `onStart`). |
| `env` | The platform's bindings for this request (the Cloudflare Workers `env`). Read them anywhere with `getEnv()`. |

`bot.fetch()` doesn't register the command menu, so cold starts stay cheap. Call `bot.setCommands()`
once after deploying — see [Deployment](/docs/guides/deployment#register-the-command-menu).

### `getEnv<T>()`

Returns the `env` passed to the most recent `bot.fetch(request, { env })`, and throws if none has
been passed yet. Database drivers and session stores accept lazy getters, so a bot created at module
scope can reach Workers bindings without importing `cloudflare:workers`:

```ts
import { createBot, getEnv } from "@teactjs/core";
import { D1Driver, d1SessionStore } from "@teactjs/cloudflare";

export const bot = createBot({
  router,
  adapter: new TelegramAdapter(),
  plugins: [storagePlugin({ driver: new D1Driver(() => getEnv<Env>().DB) })],
  session: { store: d1SessionStore(() => getEnv<Env>().DB) },
});
```

### Tokens

The token comes from `createBot({ token })`, `bot.fetch(req, { token })` or `TELEGRAM_BOT_TOKEN`.
Adapters that don't talk to a real platform can opt out of needing one: `MockAdapter` from
[`@teactjs/testing`](/docs/packages/testing) does, so tests can call `createBot()` without a token.

## Behavior notes

### Plugins from `teact.config.ts` and `createBot()`

Plugins from `teact.config.ts` and `createBot({ plugins })` are merged. If a plugin with the same
`name` appears in **both**, only the `createBot()` copy is used (with a warning), so you don't get two
driver instances or duplicated `onStart`/`onStop`. Repeating a plugin **within one list** is
intentional and every copy is kept — for example a per-user and a per-chat `rateLimit`.

### Default error screen

Every chat's screen is wrapped in an `ErrorBoundary`. When a render throws, Teact logs the error and
shows a generic "Something went wrong" message; the next update rebuilds the screen. The error
message itself is **not** shown to users, since it can carry internals such as SQL, paths or tokens.
To customize the screen, wrap your components in your own `ErrorBoundary` with a `fallback` (a node,
or `(error, retry) => node`):

```tsx
<ErrorBoundary fallback={(error, retry) => <Message text="Oops — try again." />}>
  <Profile />
</ErrorBoundary>
```

### Button presses on a new process

`onClick` handlers live in the memory of the process that rendered the message. If a press arrives
after a restart, or on a fresh serverless isolate, Teact re-renders that screen **in place** (it edits
the message rather than sending a new one) from its initial state, and logs a warning that the handler
is gone. Route buttons (`<Button route="/settings" />`) work on any instance; on serverless, prefer
them and keep screen state in `useSession` / `useStorage` so buttons keep working across instances.

### Typed `useParams`

`useParams` takes either the path template or an explicit shape. Without a type argument it returns
`Record<string, string>`:

```ts
const { id } = useParams<"/pokemon/:id">();          // typed from the path template
const { tid, mid } = useParams<{ tid: string; mid: string }>();
```
